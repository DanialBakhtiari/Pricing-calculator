# 07 — حلقه‌ی خوداصلاحی (Self-Correction Loop)

> این قلبِ «کیفیت» پروژه است. هدف: Claude Code هر واحد کار را **خودش نقد و اصلاح کند** تا معیار پذیرش برآورده شود، بدون اینکه منتظر بازخورد دستی بماند.

## ۱. چرخه

```
        ┌──────────────────────────────────────────────┐
        ▼                                              │
  ① PLAN ──▶ ② BUILD ──▶ ③ SELF-REVIEW ──▶ ④ TEST ──▶ ⑤ GATE
                                                       │
                          رد شد؟ ──▶ ⑥ DIAGNOSE & FIX ─┘ (به ② برگرد)
                                                       │
                          پاس شد ──▶ ⑦ REPORT & COMMIT
```

حداکثر **۳ دور** برای هر واحد کار. اگر بعد از ۳ دور هنوز رد است: **توقف کن**، علت ریشه‌ای و گزینه‌ها را شفاف گزارش بده (بهتر از کارِ نیمه‌درست).

## ۲. گام‌ها

### ① PLAN
- معیار پذیرش همان فاز را از `docs/06-PHASES.md` بنویس (۳ تا ۷ بولت چک‌شدنی).
- فایل‌های لمس‌شونده و توابع core مورد نیاز را فهرست کن.
- اگر منطق محاسباتی است: Test Vector مربوط را از `docs/03` کنار بگذار.

### ② BUILD
- کوچک بساز و زود تست کن. منطق در core، نمایش در UI.
- از مهارت مرتبط استفاده کن (`pricing-formulas`/`shadcn-ui-builder`/`chartjs-viz`/`pwa-and-onboarding`).

### ③ SELF-REVIEW (نقش reviewer سینیور)
چک‌لیست مهارت `self-review` را اجرا کن:
- درستی (Test Vector، حالت‌های لبه، خطاها)
- کیفیت (typecheck/lint، عدم تکرار فرمول، کامپوننت تک‌مسئولیت)
- UX/RTL/A11y (tooltip، موبایل ۳۶۰px، کیبورد/کنتراست/aria، حالت‌ها)
- محصول (معیار پذیرش فاز)

### ④ TEST
```
pnpm typecheck && pnpm lint && pnpm test && pnpm build
```
- برای موتور: Test Vectorها + پوشش ۱۰۰٪.
- برای UI: تست کامپوننت/تعامل کلیدی.
- در فازهای پایانی: `pnpm e2e` و Lighthouse.

### ⑤ GATE (Definition of Done — CLAUDE.md §۴)
همه باید سبز باشند. یک «نه» = رد.

### ⑥ DIAGNOSE & FIX
- علت ریشه‌ای را پیدا کن، نه وصله‌ی سطحی. اگر تست شکست، **چرا** را بفهم.
- برای هر باگ، یک تست رگرسیون بنویس تا دوباره برنگردد.
- بعد به ② برگرد.

### ⑦ REPORT & COMMIT
- commit با Conventional Commits.
- گزارش کوتاه: «چه ساختم / چه تستی سبز شد / چه ریسکی ماند / تصمیمات».
- تصمیم‌های معماری/وابستگی را در `docs/DECISIONS.md` ثبت کن.

## ۳. قاعده‌ی «شواهد، نه ادعا»
هرگز نگو «کار می‌کند» بدون شاهد. شاهد = خروجی سبز تست/بیلد، یا Test Vector تطبیق‌یافته. در فازهای UI، رفتار کلیدی را با تست Testing Library اثبات کن.

## ۴. کِی از Subagent استفاده کن
برای راستی‌آزمایی مستقل در فازهای حساس (موتور، فاز ۷)، یک پاس review جداگانه اجرا کن: یک‌بار با چشم «منتقد» کل دیف را در برابر `docs/03` و Definition of Done بسنج. این پاس باید **چیزی برای بهبود پیدا کند**؛ اگر هیچ ایرادی نیافت، یعنی به‌اندازه‌ی کافی سخت نگاه نکرده‌ای.

## ۵. ضدالگوها (نکن)
- ❌ علامت‌زدن «انجام‌شد» با تست قرمز یا پیاده‌سازی نیمه.
- ❌ کم‌کردن آستانه‌ی تست/پوشش برای سبز شدن.
- ❌ کپی فرمول در UI برای «سریع‌تر شدن».
- ❌ خاموش‌کردن lint به‌جای رفع علت.
- ❌ ادعای رفع باگ بدون تست رگرسیون.
